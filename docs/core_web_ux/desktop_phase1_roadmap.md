# PC 端一期开发路线图

## 1. 文档目标

本文档用于把 [desktop_prd_information_architecture.md](/Users/ancongcong/PhpstormProjects/task-gitee/docs/core_web_ux/desktop_prd_information_architecture.md) 拆解成可执行的一期开发路线图。

重点回答四个问题：

- 先做什么，后做什么
- 哪些模块可以并行
- 哪些能力必须前置
- 哪些风险需要提前兜底

## 2. 路线原则

- 先打通高频主链路，再补全外围能力
- 先做桌面独特价值，再做低频覆盖
- 先保证接口可用和状态稳定，再做复杂交互
- 低频页面允许 URL 兜底，不阻塞核心工作流上线

## 3. 一期目标范围

一期目标不是“把网站搬到桌面”，而是完成下面五条链路：

1. 打开工作台处理今天任务
2. 从任务直接开始专注
3. 专注结束后快速记录手账
4. 阅读时摘录并沉淀到笔记
5. 用快捷键、侧栏、拖拽完成高频操作

## 4. 里程碑总览

建议按 4 个里程碑推进：

1. M0 基础设施与壳
2. M1 工作台 + 任务 + 专注主链路
3. M2 阅读 + 笔记沉淀链路
4. M3 打磨与桌面增强

如果团队较小，可按 8-10 周规划。

如果团队较完整，也建议保持相同顺序，不建议颠倒依赖。

## 5. 详细阶段拆解

## 5.1 M0 基础设施与壳

### 5.1.1 目标

- 让 PC 客户端具备基本可运行框架
- 建立后续所有模块共享的能力底座

### 5.1.2 交付内容

- 客户端壳工程初始化
- 登录与会话保持
- API 请求层
- 全局状态管理
- 主路由与布局框架
- 通用 UI 组件基础
- 弹层系统
- 右侧侧栏系统
- 通知能力封装
- 快捷键系统基础
- 多窗口能力预留接口

### 5.1.3 必须完成的技术事项

- 统一 token 注入和失效处理
- 统一错误提示与异常兜底
- 页面加载骨架和空状态组件
- 列表分页/筛选的基础模型
- 命令式打开弹层与侧栏的基础机制

### 5.1.4 验收标准

- 登录成功后可进入主框架
- 任意模块可以稳定调用后端接口
- 统一弹层和右侧侧栏可复用
- 全局快捷键基础框架可用

### 5.1.5 风险

- 后端接口鉴权规则和桌面容器不一致
- 桌面端状态管理混乱，后面模块返工

### 5.1.6 结论

- M0 不能省
- 如果 M0 做得差，后面每个模块都会重复补债

## 5.2 M1 工作台 + 任务 + 专注主链路

### 5.2.1 目标

- 尽快做出“比网页更值得用”的第一版桌面体验
- 优先打通任务和专注主链路

### 5.2.2 交付内容

- 工作台首页
- 任务侧栏
- 快速新建任务
- 任务列表页
- 任务详情侧栏
- 任务编辑弹层
- 任务四象限页
- 专注主面板
- 悬浮专注窗
- 专注完成后的快速手账录入弹层

### 5.2.3 核心链路

1. 进入工作台
2. 查看今日任务
3. 新建或选择任务
4. 从任务开始专注
5. 专注结束
6. 记录成果到手账

### 5.2.4 这一阶段必须有的桌面差异化能力

- 工作台双栏布局
- 任务侧栏收起/恢复
- 栏宽拖拽
- 悬浮专注窗
- 快捷键开始/暂停专注
- 四象限拖拽

### 5.2.5 任务模块拆分建议

先做：

- 列表
- 状态过滤
- 搜索
- 快速完成
- 编辑侧栏

再做：

- 四象限
- 排期弹层
- 批量操作预留

### 5.2.6 专注模块拆分建议

先做：

- 倒计时
- 开始/暂停/结束
- 绑定任务
- 完成后手账录入

再做：

- 悬浮窗
- 托盘控制
- 系统提醒

### 5.2.7 验收标准

- 用户不需要回网页也能完成一次完整任务执行
- 悬浮专注窗稳定
- 四象限可拖拽并同步优先级
- 手账录入能承接专注结果

### 5.2.8 风险

- 任务和专注接口返回结构不一致
- 悬浮窗和主窗口状态同步复杂
- 专注状态切换容易出边界 bug

## 5.3 M2 阅读 + 笔记沉淀链路

### 5.3.1 目标

- 让桌面端从“执行工具”扩展为“输入与沉淀工具”

### 5.3.2 交付内容

- 阅读三栏页
- feed/分类导航
- 文章列表
- 文章预览/详情区
- 摘录侧栏
- 笔记列表与编辑器
- 笔记预览
- AI 处理抽屉基础版
- 从文章摘录创建笔记

### 5.3.3 核心链路

1. 进入阅读页
2. 选择 feed
3. 浏览文章
4. 选中文本摘录
5. 发送到笔记
6. 在右侧或下游页面继续整理

### 5.3.4 阅读模块拆分建议

先做：

- 左导航
- 中列表
- 右预览
- 状态切换

再做：

- 原文/清洗正文切换
- 批量操作
- AI 摘要

### 5.3.5 笔记模块拆分建议

先做：

- 列表
- 编辑器
- 预览
- 标签过滤

再做：

- AI 抽屉
- 来源卡片
- 音频工作流

### 5.3.6 验收标准

- 阅读和笔记至少形成一个闭环链路
- 用户可以从文章直接生成笔记
- 三栏布局在桌面端具有明显效率优势

### 5.3.7 风险

- 文章内容清洗和渲染差异
- 摘录与笔记引用关系未设计好，后期难扩展
- 编辑器与预览区状态同步复杂

## 5.4 M3 打磨与桌面增强

### 5.4.1 目标

- 把“能用”提升到“值得长期打开”

### 5.4.2 交付内容

- 全局搜索
- 命令面板
- 托盘增强
- 桌面通知完善
- 快捷键面板
- 最近操作面板
- 局部性能优化
- 低频页面 URL 兜底入口

### 5.4.3 优先级

优先做：

- 命令面板
- 全局搜索
- 托盘入口

后做：

- 最近操作面板
- 更完整的统计入口

### 5.4.4 验收标准

- 客户端具备明显桌面特征
- 高频用户能主要依赖键盘和面板流完成操作
- 网页端与桌面端分工清晰

## 6. 并行开发建议

## 6.1 可并行的工作流

前提是 M0 已基本稳定。

可并行拆成 4 条线：

- A 线：壳、路由、全局状态、系统能力
- B 线：工作台、任务、专注
- C 线：阅读
- D 线：笔记与手账

## 6.2 不建议并行过早拆开的内容

- 快捷键系统不要每个页面各写一套
- 弹层和侧栏系统不要模块内各自实现
- 鉴权和请求层不要边做边补

这些如果前期不统一，后面一定返工。

## 7. 周级路线建议

以下是更现实的 8 周版节奏。

- 登录会话
- 请求层
- 主路由

## 第 3 周

- 工作台首页骨架
- 任务侧栏
- 快速新建任务
- 任务列表基础版

## 第 4 周

- 任务详情侧栏
- 任务编辑弹层
- 状态过滤和搜索

## 第 5 周

- 绑定任务开始专注

## 第 6 周

- 笔记列表
- 笔记编辑器

## 第 8 周

- 命令面板

## 8. 依赖关系

## 8.1 前置依赖

下面这些必须前置：

- 登录与会话
- 请求层
- 全局状态
- 弹层系统
- 侧栏系统
- 快捷键基础框架

## 8.2 业务依赖

- 工作台依赖任务和专注接口可用
- 快速手账依赖专注完成状态与手账接口
- 阅读摘录依赖文章详情和笔记创建链路
- 命令面板依赖各模块路由和动作注册

## 9. 风险清单

## 9.1 接口层风险

- Web 接口可能存在面向页面而非面向客户端的返回结构
- 某些接口可能不够聚合，导致 PC 端多次请求拼装

建议：

- 尽早梳理一份 PC 端接口清单
- 对高频链路补聚合接口而不是前端硬拼

## 9.2 状态同步风险

- 主窗口、悬浮窗、托盘之间的专注状态同步容易出错

建议：

- 专注状态只保留一个可信源
- 其他窗口只订阅，不各自持有业务真相

## 9.3 编辑器风险

- Markdown 编辑器、预览和 AI 抽屉同时存在时，状态复杂度会上升

建议：

- 一期先保证单篇笔记稳定，不急着做太多复杂协同

## 9.4 交互分裂风险

- 如果每个模块都按自己的方式做弹层、搜索、快捷键，最终体验会很散

建议：

- 明确全局交互规范
- 优先统一基础能力

## 10. 兜底策略

## 10.1 低频页面兜底

- 设置页中可提供“打开 Web 页面”的入口
- 某些低频管理页先不原生化

## 10.2 复杂能力兜底

如果一期来不及：

- 全局搜索先做任务/笔记/文章标题搜索
- 命令面板先只支持模块跳转和新建动作
- AI 抽屉先只做摘要和创建笔记

## 10.3 风险控制原则

- 不为了赶进度牺牲主链路稳定性
- 可以少做，但不要把高频链路做得不可靠

## 11. 一期最终交付定义

一期完成时，至少应满足：

1. 用户能登录并长期使用客户端
2. 用户能在工作台完成任务与专注主链路
3. 用户能在任务和四象限之间高效管理事项
4. 用户能在阅读中摘录并写入笔记
5. 用户能感知到桌面端独特价值，而不是网页壳

## 12. 最终建议

真正的一期重点不是“页面数”，而是“链路密度”。

你应该优先追求：

- 工作台打开就能干活
- 任务和专注形成闭环
- 阅读和笔记形成闭环
- 至少有 3 个明显桌面化能力跑通

如果这个目标成立，一期就是成功的。

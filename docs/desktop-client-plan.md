# Desktop 客户端梳理与规划

## 1. 目标

这份文档用于梳理当前 `desktop/` 工程现状，并给出一套可执行的桌面客户端方案。核心目标有两个：

1. 复用现有 PC 后端接口，不重新发明一套桌面专用 API。
2. 做一个比网页更顺手、更稳定、更有桌面感的客户端，而不是简单“套壳”。

结论先说：

- 后端接口层已经具备复用基础，优先统一走 `/api/v2/*`。
- 当前 `desktop/` 已经有 Electron 原型，但更接近第一版 Demo，还没有收敛成可长期维护的正式客户端。
- 桌面端应当主打“任务 + 专注 + 日历 + 快速捕获 + 提醒”这条主链路，先做高频刚需，不要一开始把 PC 全量功能搬过去。

## 2. 当前仓库现状

### 2.1 现有目录

- 桌面工程目录：`desktop/`
- 后端 API 路由：`routes/api.php`
- Web 路由：`routes/web.php`
- Hybrid token 接入说明：`docs/hybrid-auth-client.md`
- 现有前端 token client：`public/js/hybrid-api-client.js`

### 2.2 desktop 当前已经有的能力

从现有代码看，桌面端已经不是空项目，已有下面这些基础：

- Electron 主进程：窗口、托盘、通知、悬浮窗、配置存储
- Renderer 页面：登录、概览、任务、番茄钟、日历、笔记、统计入口
- API 调用层：直接请求 `https://pretask.congcong.us/api/v2`
- 本地 token 存储：通过 `electron-store` + `preload.js` 暴露给渲染层
- 桌面特性原型：托盘菜单、悬浮窗、通知、快捷键

说明当前方向本身是对的：不是把 PC 页面塞进 Electron，而是已经开始做独立桌面交互。

### 2.3 desktop 当前暴露出的主要问题

当前实现能说明方向，但距离“可长期维护的正式产品”还有明显差距：

1. 认证链路没有完全对齐现有 hybrid token 方案。
当前 `desktop/renderer/js/api.js` 只保存了 `access_token` 思路，但仓库里的标准方案已经是 `access_token + refresh_token`，并且 `public/js/hybrid-api-client.js` 已经实现了 `401 -> refresh -> retry`。

2. API 层重复造了一套简化客户端。
现在桌面端自己写了 `ApiService`，但没有完全继承现有 PC token 机制、错误处理规范、刷新逻辑和存储键约定，后面容易出现 Web 正常、Desktop 失效的分叉。

3. 一部分界面已经有样子，但模块完成度不一致。
任务、概览、日历、番茄钟都有代码；设置、搜索、通知面板、编辑任务等仍有较多占位实现。

4. 目前更像“单页脚本拼装”，工程化不够稳定。
例如渲染层是直接 `<script src="...">` 引入，但 `desktop/renderer/js/app.js` 里仍有 `export default app;`，这类写法在当前加载方式下是不一致的。

5. 离线能力还停留在目标描述，没有真正落地。
README 和 DESIGN 提到了离线支持，但当前实现主要还是在线直连 API，没有真正的本地缓存模型、同步队列、冲突策略。

6. 功能范围有扩张风险。
PC 站点功能很多，包含任务、笔记、Feed、课程、LLM、积分商城等。桌面端如果一开始全搬，会很重，也很难做出“优美实用”的体验。

## 3. 现有接口是否适合复用

结论：适合，而且应该强制复用。

### 3.1 API 已经具备桌面端复用条件

`routes/api.php` 里 `/api/v2` 已经覆盖了桌面端核心高频模块：

- 认证：`/auth/login` `/auth/refresh` `/auth/logout` `/auth/me`
- 任务：`/tasks` `/tasks/all` `/tasks/tab-counts` `/tasks/priority` `/tasks/parent-tasks`
- 专注：`/focuss` `/focuss/start` `/focuss/today` `/focuss/tab-counts`
- 日历：`/calendar`
- 笔记：`/notes`
- 统计：`/statistics`
- 设置：`/settings`

这已经足够支撑一个完整的桌面客户端 MVP。

### 3.2 token 模型也已经适合多端

仓库里已经明确存在统一方案：

- `UAT`：用户登录 token
- `URT`：refresh token
- `PAT`：个人访问 token
- 中间件：`hybrid.token:read` / `hybrid.token:write`

对桌面端来说，建议：

- 用户正常登录场景：使用 `UAT + URT`
- 开发调试或脚本集成：可额外支持 `PAT`
- 不建议桌面客户端继续依赖传统 web session

### 3.3 不建议复用 PC 页面，只复用 PC 接口

“复用 PC”这里要分清层级：

- 应复用：后端 API、认证体系、业务字段、状态枚举、返回格式
- 不应直接复用：SSR 页面、jQuery 交互、PC 页面布局

原因很简单：

- 桌面端的优势在于快速捕获、悬浮提醒、托盘运行、专注模式、键盘流
- 这些体验如果直接照搬 PC 页面，会失去桌面产品价值

## 4. 建议的桌面端产品定位

建议把桌面客户端定位成：

“以任务执行和专注管理为核心的高频工作台”

不是 PC 的全量镜像，而是 PC 里的高频核心子集 + 桌面增强能力。

### 4.1 第一优先级功能

这部分建议作为正式桌面版首批能力：

1. 登录与多端会话
2. 今日概览
3. 任务列表
4. 快速创建任务
5. 任务完成/延期/切换优先级
6. 番茄钟与专注记录
7. 日历视图与任务到期提醒
8. 系统通知、托盘、悬浮窗

### 4.2 第二优先级功能

这部分适合在 MVP 稳定后补：

1. 笔记
2. 搜索
3. 通知中心
4. 设置中心
5. 简单离线缓存
6. 最近操作历史

### 4.3 暂不建议第一阶段进入桌面端的功能

除非你明确要做“全家桶工作台”，否则这部分先不要急着搬：

1. Feed / 阅读器
2. 积分商城
3. 课程系统
4. LLM 全功能后台
5. 各类低频后台管理页面

这些功能更适合继续放在 Web。

## 5. 建议的桌面端信息架构

建议桌面端收敛成 5 个主视图：

### 5.1 Today

首页不做大而全仪表盘，建议改成更直接的“今日工作台”：

- 今日待办数
- 正在进行任务
- 即将到期任务
- 今日专注时长
- 一键开始番茄钟
- 一键快速记录

### 5.2 Tasks

桌面端最重要的视图，建议重点打磨：

- 左侧过滤：全部、进行中、已完成、已折叠
- 顶部切换：工作 / 生活 / 学习
- 列表支持键盘导航
- 支持快速编辑、完成、延期、移动优先级
- 支持“父任务 -> 子任务”层级展示

### 5.3 Focus

桌面端应比网页强：

- 番茄钟主界面
- 当前任务绑定
- 专注中悬浮窗
- 结束提醒
- 自动写入 `/focuss` 记录

### 5.4 Calendar

建议作为“任务时间视图”，而不是复杂日程系统：

- 展示有截止时间的任务
- 展示 focus 记录或计划块
- 点击日期快速创建任务
- 支持今天、本周、月视图

### 5.5 Quick Capture

这才是桌面端差异化重点：

- 全局快捷键呼出
- 输入一句话快速建任务
- 可选设优先级/日期/模式
- 创建成功后不打断当前工作

## 6. 技术方案建议

### 6.1 后端接口策略

统一原则：

- 只走 `/api/v2/*`
- 不再新增一套 `/api/desktop/*`
- 不再依赖旧 `/task` `/focus` 这类 Web 风格接口

这样做的好处：

- Web / Desktop / 后续移动端都共享一套接口语义
- 权限、认证、日志、限流更容易统一
- 文档、测试、联调成本更低

### 6.2 认证策略

建议桌面端对齐现有 hybrid token 方案：

1. 登录时调用 `/api/v2/auth/login`
2. 保存 `access_token + refresh_token`
3. 所有请求统一自动带 `Authorization: Bearer ...`
4. 收到 `401` 自动调用 `/api/v2/auth/refresh`
5. refresh 成功后自动重放失败请求
6. refresh 失败后清空 token 并回到登录页

建议直接复用 `public/js/hybrid-api-client.js` 的机制，至少复用它的设计，不要让桌面端继续维护一套简化版 token 刷新逻辑。

### 6.3 API 封装策略

建议把桌面端 API 分成两层：

1. `transport` 层
负责 token、refresh、错误码、重试、超时、网络状态

2. `domain service` 层
例如：

- `authService`
- `taskService`
- `focusService`
- `calendarService`
- `settingsService`

这样桌面 UI 不直接拼 URL，后面维护成本会低很多。

### 6.4 本地数据策略

第一阶段不要急着做“完整离线优先”，建议先做“弱离线”：

- 本地缓存最近一次任务列表
- 本地缓存用户设置
- 本地缓存当前番茄钟状态
- 断网时允许查看缓存
- 恢复网络后重新拉取服务端数据

第二阶段再做写操作队列：

- 离线创建任务
- 离线完成任务
- 自动重放同步
- 冲突提示

### 6.5 UI 技术建议

如果继续维护当前桌面端，建议尽快做一次工程收敛：

- 统一模块加载方式
- 去掉当前脚本直引和模块语法混用问题
- 补齐错误态、空态、骨架屏
- 把 modal / toast / settings / notification 抽成公共组件

如果你打算认真把桌面端做成长期产品，我更建议：

- 保留 Electron
- 渲染层升级到更稳定的组件化前端方案
- 例如 `Vue` 或 `React`

原因不是“时髦”，而是当前桌面端已经进入多视图、多状态、多交互阶段，继续用脚本拼接很快会失控。

## 7. 视觉与交互方向建议

你提的目标是“比较优美实用”，这里建议不要走普通后台皮肤路线，而是走“轻专注工作台”。

### 7.1 关键词

- 安静
- 清晰
- 轻重量
- 强层级
- 快速输入
- 少打扰

### 7.2 视觉方向

建议：

- 主色偏深青绿或墨蓝，不要做成传统 SaaS 紫色模板
- 大面积留白 + 卡片层级 + 柔和阴影
- Today 页强调节奏感，Tasks 页强调密度与可扫读性
- 专注页可更沉浸，允许更深背景和更少控件

### 7.3 交互重点

桌面端不应该只是“好看”，更关键是顺手：

- 快捷键能覆盖 60% 高频动作
- 快速新增任务必须比网页更快
- 完成任务、开始专注、查看今日安排都要一跳直达
- 托盘和悬浮窗要真正有用，不是摆设

## 8. 推荐实施路线

### Phase 1：整理基础层

目标：让桌面端先稳定跑起来

建议内容：

1. 认证改成 `access_token + refresh_token`
2. API 层对齐 hybrid token client
3. 清理脚本加载和模块结构
4. 补齐错误处理和空态
5. 梳理配置项和环境变量

阶段产出：

- 能稳定登录
- token 自动续期
- 任务/番茄钟/日历接口可长期使用

### Phase 2：做 MVP 核心链路

目标：做出真正可用的桌面客户端

建议内容：

1. Today 工作台
2. 任务列表与快速新增
3. 番茄钟主链路
4. 到期提醒与桌面通知
5. 托盘和悬浮窗联动

阶段产出：

- 用户每天能真正开着用
- 桌面端价值明显区别于网页

### Phase 3：补桌面增强

目标：拉开和网页端的体验差距

建议内容：

1. 全局快捷键快速捕获
2. 本地缓存和弱离线
3. 搜索和命令面板
4. 更好的统计和专注复盘
5. 设置中心

### Phase 4：决定是否扩展功能面

到这一步再评估是否要加入：

- 笔记
- 阅读
- 学习计划
- AI 助手入口

不要提前把范围做大。

## 9. 我对这个项目的具体建议

如果你的目标是“尽快做出一个漂亮且真能用的桌面客户端”，我建议你这样定策略：

1. 后端层面完全复用现有 `/api/v2`
2. 桌面端只做高频场景，不做 PC 全量复制
3. 第一版只打磨 `任务 + 专注 + 日历 + 快速捕获 + 通知`
4. 先把认证和 API 基础层收敛，再谈 UI 打磨
5. UI 上走“专注工作台”路线，不走传统后台风

## 10. 下一步可直接执行的任务

如果按落地优先级排，我建议下一步这样做：

1. 重构桌面端认证和 API 客户端，彻底接入 refresh token
2. 输出一版桌面端信息架构和界面草图
3. 重做 `Today / Tasks / Focus` 三个核心页面
4. 再接托盘、悬浮窗、通知的完整联动
